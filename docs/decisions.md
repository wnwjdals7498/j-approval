# j-approval 설계 결정

j-approval만의 설계 결정을 적는다. 제품군 공통 결정은 [`j-groupware/docs/architecture.md`](https://github.com/wnwjdals7498/j-groupware/blob/main/docs/architecture.md)(이하 architecture.md)의 S 번호를 따르고 여기서는 링크만 한다. PMT는 통합 project `j-groupware-suite`의 분류 `j-approval`에 같은 번호로 기록한다(S16).

정리일: 2026-10-07. 통합 정리에서 중복 내용을 공통 문서로 옮겼다. 결정 번호는 바뀌지 않았다.

## 0. 범위

- **범위:**
  - 고객(tenant)과 하위 회원을 위한 내부 전자결재 백엔드 API다.
  - 결재선은 j-groupware가 조직도로 만들어 상신 요청에 담아 보낸다. 처리는 순차 N단계이고, 문서는 1종이다.
  - 화면은 j-groupware "결재" 메뉴다(j-groupware 결정 12).
- **완료 기준:**
  1. `approval:use`를 가진 하위 회원이 문서(제목·본문)를 결재선과 함께 상신한다.
  2. 결재선의 각 단계 지정자만 순서대로 승인·반려한다. 마지막 단계 승인 시 승인, 어느 단계든 반려(사유 필수) 시 반려로 종결된다.
  3. 작성자와 결재자가 문서 상태와 단계별 이력을 조회한다.
  4. 다른 tenant의 문서·결재선·계정은 보이지 않고 처리할 수 없다.
- **배치:** 고객 서버의 선택 서비스다. API는 내부 포트로만 열고 j-groupware가 중계한다.
- **관련 공통 결정:** S2(서비스·DB), S3(권한), S4(토큰 전달), S5(화면), S8~S14.

## 1. 서비스 대상과 형태

### 결정 1. 서비스 대상
- **결정 (사용자):** 가입한 고객과 그 하위 회원을 위한 내부 전자결재다. 손님은 관계없고 j-customer-auth-db에 의존하지 않는다.

### 결정 2. 서비스 형태
- **결정 (사용자):** 백엔드 API(`apps/server`, `packages/contracts`)만 만든다. 화면은 j-groupware 페이지다(S5).

## 2. 결재선

### 결정 3. 결재자 기준
- **결정:** 결재선 각 단계에 지정된 사람만 그 단계를 처리한다. role은 메뉴 권한만 뜻하고 결재 처리 자격이 아니다.

### 결정 4. 결재선 입력과 검증
- **결정:**
  - 결재선은 j-groupware가 만든다. 기본 규칙(소속 부서장 → 상위 부서장, 작성자 제외)과 커스텀 편집은 j-groupware 결정 12다(사용자).
  - j-approval은 상신 요청의 결재선(단계 순서대로 j-auth 회원 id)을 검증하고 스냅샷으로 저장한다.
    - 검증 규칙: 1단계 이상, 같은 회원 중복 없음, 작성자 본인 제외. 위반하면 400이다.
    - 이후 조직도가 바뀌어도 진행 중인 문서는 영향을 받지 않는다.
  - j-approval은 j-groupware를 호출하지 않는다.
  - 합의·병렬·참조는 backlog다.

### 결정 5. 조직도 위치
- **결정:** 조직도는 j-groupware DB에 있다(j-groupware 결정 12). j-approval은 조직도를 저장하지도 조회하지도 않는다.

### 결정 6. 결재 참여자 범위
- **결정:**
  - 결재선에는 같은 tenant의 고객 realm 계정만 넣는다. 커스텀 후보는 j-groupware 조직도에 등록된 계정(미배치 포함)이다(사용자). 외부인·손님은 제외한다.
  - j-approval은 회원 id가 실제로 있는지 따로 조회하지 않는다. 처리 요청 토큰의 `sub`·`tenant`가 스냅샷의 지정자와 맞아야만 처리되므로, 잘못된 id가 들어가도 다른 tenant 계정은 처리할 수 없다. 그 문서는 진행되지 않을 뿐이다.

### 결정 7. 문서·상태 모델
- **결정:**
  - 문서는 1종(제목·본문)이다. 상신하면 진행중이 되고, 현재 단계 지정자가 승인하면 다음 단계로 넘어간다.
  - 마지막 단계 승인 시 승인, 어느 단계든 반려 시 반려로 종결한다. 반려 사유는 필수다. 종결 후에는 변경할 수 없다(409).
  - 이력은 append-only다: 상신·열람·승인·반려, 행위자·단계·시각.
  - 동시 처리는 문서 행 잠금(또는 버전 비교)으로 막는다.

## 3. 인증과 권한

### 결정 8. API 호출 인증
- **결정:** j-groupware가 전달한 Bearer를 j-auth 기준으로 검증한다(aud `j-approval`, S4). `approval:use` 보유와 결재선 지정 여부를 직접 검사한다. tenant는 토큰 claim에서만 정한다.
- **이유:** j-customer-auth-db·j-mail과 같은 방식이다.

### 결정 9. 기능 권한
- **결정:** role client `j-approval`의 `approval:use`(결재 메뉴·상신·내 문서·결재함)를 쓴다. 조직도 편집 `org:manage`는 기본 서비스 `j-groupware`에 있다(S3 카탈로그).
- **이유:** 결재 처리 자격은 결재선(결정 3)이 정하므로 role은 메뉴 권한만 다룬다.

## 4. 데이터·검증·배포

### 결정 10. 결재 저장소
- **결정:** 고객 서버 PostgreSQL에 database `jgw_approval`과 전용 계정을 둔다(S2, S9). 모든 테이블에 `tenant_id`를 둔다(S8).

### 결정 11. 저장소·테스트·배포
- **결정:**
  - S11 골격을 쓰고, contracts는 레지스트리에 게시한다(S10).
  - Vitest로 실제 j-auth·Keycloak·PostgreSQL을 대상으로 검증한다. 결재선은 테스트가 상신 요청에 직접 넣으므로 j-groupware 서버가 필요 없다.
  - 테스트 회원(작성자, 결재자 2명 이상, 결재선 밖 회원)은 j-auth 회원 관리 API로 만들고 지운다. 권한 없는 회원은 `a-member`, 다른 tenant는 `b-admin`이다(S12).
  - 화면 e2e는 j-groupware G16에서 한다. 로컬 완료 후 고객 서버 VM에서 다시 검증한다(S13).
